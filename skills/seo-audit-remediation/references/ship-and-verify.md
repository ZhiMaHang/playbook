# 实施、上线核对、复测

修完要验两次：上线当天核对「改对了没有」，几周后复查「改了有没有用」。只做第一次，不知道有没有用；只做第二次，出了问题也分不清是没改对还是改了没用。

分工：本技能做第一次验收（上线核对），以及「复测」：用同一套评分表重新打分、核对改动是否真的上线、修过的网址有没有回到已收录。平台数据的效果复查（展示、点击、排名、询盘有没有朝预期方向变）归 **seo-analytics-reporting** 技能：冻结基线，在第 28、56、90 天各看一次。本技能在问题卡里写好基线和预期方向，交给它，不在这里另做一套。

## 1. 预览

负责人说「出个页面看看效果」，要的是一个能直接打开、能反复改的预览，不是走上线流程。提交、开合并请求，在很多站上就等于「要上线了」，负责人会很敏感。

预览有两种做法：

| 做法 | 适用 | 要点 |
|---|---|---|
| 本地跑整站 | 改到后端逻辑、数据库、路由 | 用线上数据库的只读导出；本地域名要能让程序识别出是哪个站点、哪种语言 |
| 代理线上页面，再套用改动 | 只改模板、样式、脚本、文案 | 代理只监听本机端口；页面请求转到线上，HTML 按分支模板改写，静态资源用本地文件应答 |

两种预览都要做到：

- **非 GET 请求一律不转发**，表单就不会真的提交到线上；
- 统计、广告的域名替换掉，不污染线上数据；
- 预览页加 `noindex`，这个标记只用在预览，上线代码里不能有；
- 多宽度检查：390、768、1024、1440、1920。

代理预览测不出模板在别的数据分支下会不会报错。改到模板分支的，上线前要在真实的模板引擎里跑一遍改动片段，并按数据差异分层抽样（见第 3 节）。

预览给负责人看的时候，附上两样东西：这一版改了什么（对应哪几张问题卡），以及按评分表估的分（注明是内部检查口径）。

## 2. 审批

- 提交代码、开合并请求、合并、发布、改后台数据，都要负责人用原话明确说了才做。谁批、怎么批，见站点档案第 3 节。
- 一次批准只管那一次，不能顺延到下一步。
- 含糊的话（「继续」「再试一次」「好」）先问清楚指的是哪一步。
- 转述来的许可（「某某说可以合并」）不算。要本人在当前对话里说。
- 删除或关闭访客看得见的板块，单独请负责人确认。不能写进打包方案的说明里，因为负责人往往只看选项标题。

## 3. 改代码

- 遵守站点档案「已知坑」。
- 用到的函数、配置键、数据 ID，先在代码里搜到定义或在数据库里查到，再用。语法检查不执行代码，拦不住「函数不存在」。
- 找数据按 ID，不按标题或网址别名。多语言站、姊妹站之间，标题和别名常常不一样，按名字找会静默失效：不报错，板块直接消失。
- 全局改动（中间件、公共头尾模板、全站助手函数、结构化数据生成程序）先在本地跑通至少一个样页，再提交。
- **按数据差异分层抽查**：模板加数据生成的页面，样板页过了不代表别的品类也过。按品类或栏目路径分层，每层都有样本，专门覆盖字段为空、没配内容的分支；测试网址和正式网址各跑一次。
- 发布有白名单或排除清单的，先确认改的文件在发布范围内。
- 静态资源有版本号的，改了就升版本号，并更新对应的清单。
- 把本次的验收项写成能重跑的检查脚本，随改动一起提交，例如某页的 Title 是否等于 X、某段结构化数据能否解析。下次有人改坏了，检查会报出来。

给开发提技术需求，用 [technical-seo.md](technical-seo.md) 第 1 节的需求单六栏（现象、范围、证据、依据、期望、验收）。

## 4. 改后台数据

1. 读出要改的记录的旧值，存一份备份（文件名带日期）。
2. 能试运行（dry-run）的先试运行，看清会改哪些记录、哪些字段。
3. 只改涉及的字段。先确认批量接口会不会把没传的字段清空或改成默认值。
4. 写完读回，和预期逐字比对。
5. 在工作日志里记下：改了哪些记录的哪些字段、旧值备份在哪、怎么恢复。

后台改动通常立即生效，没有「合并」这道闸，所以审批要更严，不能更松。

## 5. 两次验收的时间线

| 时间点 | 做什么 |
|---|---|
| 上线前 | 把验收标准写进问题卡：查什么、何时查、什么算合格 |
| 上线当天 | 第一次验收：核对十项（第 6 节）。改动生效了吗、带出新问题没有、没打算改的页面有没有被动到 |
| 1–2 周 | 看收录：修过的网址回到已编入；GSC「验证修复」约两周出结果；请求编入索引不保证收录，反复请求不会更快 |
| 第 28、56、90 天 | 效果复查，交 seo-analytics-reporting（冻结基线后按它的方法看）；Google 说改动生效要几小时到几个月不等 |
| 遇到核心更新 | 推完再等至少一周再比，不然会把更新的影响算到自己的改动上 |

## 6. 上线当天核对十项

**流水线显示成功，不等于页面已经变了。** 每项都到线上真实页面核对：

| # | 核对项 | 怎么核对 |
|---|---|---|
| 1 | 改动生效 | 线上页面里能找到这次改动的新内容（打开源码搜新加的标识，或执行 `document.body.innerHTML.includes('…')`）；不看发布流程是否显示成功；部署日志里能看到目标文件，每个站点、每个部署任务都成功 |
| 2 | 状态码与跳转 | 新页面返回 200；旧网址一步 301 到新网址；下线的返回 404 或 410 |
| 3 | noindex | 正式页没有 noindex（meta 和响应头都查）；测试页本身仍是 noindex |
| 4 | 规范网址 | canonical 指向正式网址，不指向测试网址 |
| 5 | 标题、描述、H1 | 是新版，没被模板或后台旧值覆盖；站点的标题后缀规则照常生效（按最终渲染结果核对） |
| 6 | 结构化数据 | 每段都能解析，同一段只有一份；富结果测试有效；问答和可见文字逐字一致 |
| 7 | 站点地图 | 含新网址，旧网址已去掉；网址写法和 canonical 一致；需要时在后台重新生成 |
| 8 | 链接 | 改动页全部链接都是 200，没有指向测试网址的链接 |
| 9 | 各站和各语言 | 改了的版本都核对；没打算改的版本、姊妹站、同类页面抽几页确认没变 |
| 10 | 缓存与身份 | 有缓存层的站先加随机参数看源站，等缓存过期再看正常网址；用 Googlebot、必应、百度的身份各抽查一次；真人手机也看一次，真人和爬虫拿到两套页面的写成现存风险 |

结果写进问题卡的「验收」栏：时间、核对人、结果、截图。

**源站已是新版、公网还是旧版**：这是缓存层的问题。要拿出证据：部署日志、源站请求结果、另一个站点或语言已经生效。然后提醒有权限的人处理。清 CDN、清编译缓存、重启服务这类操作，按站点档案的权限来，不要擅自做。

**部署报错，或者明显比平时慢**：先请求关键页面看有没有报错。有问题就先回滚（revert 到上一个版本），回滚稳定后再查原因。不要在线上边查边修。

**重跑旧的部署前**：先看主分支上有没有更新的部署。有的话不要重跑旧的，否则会把新版本冲回旧版本。

## 7. 搜索平台侧

- **谷歌**：Search Console 网址检查，点「测试实际网址」看渲染后的 HTML 里有没有新内容，然后请求编入索引（少量重要页）；修好一类问题后在网页报告里点「验证修复」；重新提交站点地图；一周内用富结果测试检查结构化数据。
- **百度**：资源平台普通收录推送新网址（看 success 和 remain）；站点地图按 5 万网址、10MB 切分逐个提交，不用索引文件；抓取诊断抽查改过的模板。旧网址下线的，先返回 404 再提交死链；换网址结构的用「网站改版」工具。
- **必应等**：IndexNow 推送新增、更新、删除的网址（跳转和 404 的也推）。
- 新的网址结构、批量 301，要在报告里标出预计的波动期。

## 8. 记录

每次上线，在站点工作日志里写清：

- 改了什么（哪些页面、哪些文件、哪些后台记录，对应哪几张问题卡）；
- 什么时候生效；
- 怎么回滚（命令、或者恢复哪份备份）；
- 核对结果：几项，全过还是哪项没过；
- 没解决、另列进问题清单的问题。

## 9. 复测（本技能）与效果复查（交出去）

**复测**，本技能做：

- 用同一个脚本、同一张评分表（同一版本）、同一种正文统计方法重跑内部评分，和上次逐项对比，表头写明两次的日期和评分表版本。评分上涨只说明页面更符合我们定的标准，不说明有效果。
- 按问题卡逐张核对：改动是否真的在线上、是否带出新问题、修过的网址是否回到已收录（网址检查、编入索引报告「验证修复」的结果）。没修好的退回问题清单，写明原因。
- 复测指标表（报告里放一张）：指标、现在、目标、怎么看、复查日期。例：重复标题数、非 200 网址数、站点地图里的非规范网址数、薄页数量、带参数的可收录页面数、平均分。

**效果复查**，交 seo-analytics-reporting 技能：

- 交接时给它三样：每张问题卡的基线（审计时记下的后台数据：展示、点击、点击率、平均排名、收录，带日期）、改动日期、预期哪个指标朝哪个方向变。
- 它的做法是冻结基线，在第 28、56、90 天各看一次，排除季节、更新和统计口径断点后给结论。本技能不重复做这一块。
- 改动安排上配合它：一次只改一处，同一页面的下一处改动等这一轮复查完再动，否则说不清是哪一处起了作用。
- 它判为「无效」或「待观察」的问题，回到本技能阶段 1 重新找原因。
