# 实施、上线、核对、复测

## 1. 预览

负责人说「出个页面看看效果」，要的是一个能直接打开、能反复改的预览，不是走上线流程。提交、开合并请求，在很多站上就等于「要上线了」，负责人会很敏感。

预览有两种做法：

| 做法 | 适用 | 要点 |
|---|---|---|
| 本地跑整站 | 改到后端逻辑、数据库、路由 | 用线上数据库的只读导出；本地域名要能让程序识别出是哪个站点、哪种语言 |
| 代理线上页面，再套用改动 | 只改模板、样式、脚本、文案 | 代理只监听本机端口；页面请求转到线上，HTML 按分支模板改写，静态资源用本地文件应答 |

两种预览都要做到：

- **非 GET 请求一律不转发**，表单就不会真的提交到线上；
- 统计、广告的域名替换掉，不污染线上数据；
- 预览页加 `noindex`，这个标记只用在预览，上线代码里不能有；
- 多宽度检查：390、768、1024、1440、1920。

预览给负责人看的时候，附上两样东西：预估分，以及这一版改了什么。

## 2. 审批

- 提交代码、开合并请求、合并、发布、改后台数据，都要负责人用原话明确说了才做。谁批、怎么批，见站点档案第 3 节。
- 一次批准只管那一次，不能顺延到下一步。
- 含糊的话（「继续」「再试一次」「好」）先问清楚指的是哪一步。
- 转述来的许可（「某某说可以合并」）不算。要本人在当前对话里说。
- 删除或关闭访客看得见的板块，单独请负责人确认。不能写进打包方案的说明里，因为负责人往往只看选项标题。

## 3. 改代码

- 遵守站点档案「已知坑」。
- 用到的函数、配置键、数据 ID，先在代码里搜到定义或在数据库里查到，再用。语法检查不执行代码，拦不住「函数不存在」。
- 找数据按 ID，不按标题或网址别名。多语言站、姊妹站之间，标题和别名常常不一样，按名字找会静默失效：不报错，板块直接消失。
- 全局改动（中间件、公共头尾模板、全站助手函数）先在本地跑通至少一个样页，再提交。
- 发布有白名单或排除清单的，先确认改的文件在发布范围内。
- 静态资源有版本号的，改了就升版本号，并更新对应的清单。
- 把本次的验收项写成能重跑的检查脚本，随改动一起提交，例如某页的 Title 是否等于 X、某段结构化数据能否解析。下次有人改坏了，检查会报出来。

## 4. 改后台数据

1. 读出要改的记录的旧值，存一份备份（文件名带日期）。
2. 能试运行（dry-run）的先试运行，看清会改哪些记录、哪些字段。
3. 只改涉及的字段。先确认批量接口会不会把没传的字段清空或改成默认值。
4. 写完读回，和预期逐字比对。
5. 在工作日志里记下：改了哪些记录的哪些字段、旧值备份在哪、怎么恢复。

后台改动通常立即生效，没有「合并」这道闸，所以审批要更严，不能更松。

## 5. 上线核对

**流水线显示成功，不等于页面已经变了。** 必须到线上真实页面核对。

| 核对项 | 怎么查 |
|---|---|
| 文件真的同步了 | 部署日志里能看到目标文件；每个站点、每个部署任务都成功 |
| 新内容在线上 | 打开源码，搜新加的标识（或在页面上执行 `document.body.innerHTML.includes('…')`） |
| 标签 | Title、描述、H1、canonical、hreflang、robots 标签逐项和预期比对 |
| 结构化数据 | 每段都能解析，问答和可见文字逐字一致 |
| 状态码和跳转 | 新网址 200，旧网址 301 到对的地方，下线的 404 或 410 |
| 多版本 | 每个语言版本、姊妹站、多种 UA（真人手机、搜索引擎爬虫、AI 爬虫） |
| 链接 | 改动页全部链接都是 200 |
| 站点地图 | 新增或改了网址的页面已在站点地图里，网址写法和 canonical 一致 |
| 没有误伤 | 没改的同类页面、其他站点、其他语言保持原样，抽几页比对 |

**源站已是新版、公网还是旧版**：这是缓存层的问题。要拿出证据：部署日志、源站请求结果、另一个站点或语言已经生效。然后提醒有权限的人处理。清 CDN、清编译缓存、重启服务这类操作，按站点档案的权限来，不要擅自做。

**部署报错，或者明显比平时慢**：先请求关键页面看有没有报错。有问题就先回滚（revert 到上一个版本），回滚稳定后再查原因。不要在线上边查边修。

**重跑旧的部署前**：先看主分支上有没有更新的部署。有的话不要重跑旧的，否则会把新版本冲回旧版本。

## 6. 搜索平台侧

- **谷歌**：Search Console 网址检查，看「已呈现的 HTML」里有没有新内容，然后请求编入索引；重新提交站点地图；一周内用富媒体测试检查结构化数据。
- **百度**：资源平台提交站点地图、普通收录推送、抓取诊断。旧网址下线的，提交死链。
- **必应等**：IndexNow 推送。
- 新的网址结构、批量 301，要在报告里标出预计的波动期。

## 7. 记录

每次上线，在站点工作日志里写清：

- 改了什么（哪些页面、哪些文件、哪些后台记录）；
- 什么时候生效；
- 怎么回滚（命令、或者恢复哪份备份）；
- 核对结果：几项，全过还是哪项没过。

## 8. 复测

- 用同一个脚本、同一张评分表、同一种正文口径重跑，和上次结果逐项对比，表头写明两次的日期。
- 复测指标表一栏一项：指标、现在、目标、怎么看、复查日期。
  - 例：收录量、真蜘蛛抓取次数、薄页数量、带参数的页面数、重复标题数、主题词组密度、平均分。
- 观察窗口：收录看 1–2 周；曝光和查询词扩展看 4–8 周；排名和询盘要更久。
- 到了复查日期，按表逐项查，把结果写进下一版报告。没达到目标的，回到阶段 1 重新找原因。
- 评分上涨只说明页面更符合我们定的标准，不说明有效果。效果以平台数据为准。
