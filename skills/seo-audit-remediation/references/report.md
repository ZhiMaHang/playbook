# 诊断报告

每次诊断交两样：

- **Markdown 报告**：存档用，放在站点工作目录；
- **HTML 看板**：给负责人看。把数据写成 JSON（字段见 [../assets/report-template.html](../assets/report-template.html) 头部注释），运行 `node scripts/build_report.mjs 数据.json 报告.html` 生成静态页。生成出来的页面不靠脚本就能显示全部内容。环境里有发布网页的工具时，默认私有发布，把链接给负责人。

两份内容要一致：先写 Markdown，再从它整理出 JSON。生成后打开看一眼，确认各节都有内容。

文件命名：`站点_审计对象_YYYYMMDD`；截图和导出放在同名文件夹，截图能看到网址和日期；改版后另存新版，旧版不覆盖。

## 结构：五部分

| 部分 | 写什么 | 给谁看 | 篇幅 |
|---|---|---|---|
| 1. 摘要 | 结论三句、卡点、关键数字、P0 / P1、要拍板的事、下一步 | 负责人、管理层 | 1 页 |
| 2. 范围与方法 | 站点、语言、页面清单与抽样、日期、工具和版本、抓取身份、评分表版本、缺的数据 | 要复核的人 | 半页 |
| 3. 问题清单 | 根因（不超过 3 条）；每个问题一张十栏问题卡，按级别排序 | 开发、写手、站点负责人 | 主体 |
| 4. 路线图 | P0–P3 分批：每批做什么、谁负责、什么时候验收；已达标项；待拍板 | 站点负责人 | 1 页 |
| 5. 附录 | 内部检查评分、逐页评分表、复测指标、导出数据、截图、给平台的说明草稿 | 要核对的人 | 不限 |

### 1. 摘要（只写一页）

很多人只读这一页，所以读完要能做决定。

- **抬头**：审计对象 · 站点 · 日期；两三个关键基线：展示、点击、收录，带日期和来源。
- **结论三句**：卡在哪一环；为什么；最该先做什么。
- **关键数字**：3–5 个，每个带日期和来源。
- **P0 / P1**：最多 5 条，编号对应问题清单。
- **要拍板的事**：每件写清选项 A / B 和建议，不只抛问题。删除或关闭可见内容、改定稿口号、换网址、换域名这类，各自单独成项。
- **下一步**：谁、什么时候做完、哪天复查。

别写进摘要：工具导出的原始列表（放附录）；没有证据的猜测；还没核实的本站口径；内部评分和自估的整改后分数（放附录，注明是检查口径）。

例外：用户明确要的就是「这页能打多少分」，在结论三句之后加一句「按评分表 vN 得 X 分，这是内部检查口径，不代表效果」，分项仍放附录。

### 2. 范围与方法

- 站点、语言版本、姊妹站；页面类型、每类多少网址、抽了哪几页、为什么抽它们；没查的模板写「未检查」，读者才知道结论的适用范围。
- 日期；数据来源（抓取、日志、平台、工具、代码版本）；抓取用的 UA、是否渲染 JS。
- 评分表版本和改过的阈值；测量方法：正文范围、重合率、长度。
- 缺了哪些数据，相关项怎么处理（剔除还是保守给分）；哪些数字是近似值。
- 依据分三类标注：官方规则写文档名和日期；经验值写「经验值」；推断写「推断」。
- 一句话说明：评分标准是自定的，不是搜索引擎的官方分；页面分高不等于能排上。

### 3. 问题清单

- **根因**：不超过 3 条。每条从现象到原因，证据链写完整。
- **问题卡**：每个问题一张，十栏缺一不可：编号、现象、证据、范围、依据、环节、建议、级别、负责人、验收。格式和示范见 [severity.md](severity.md) 第 6 节。按 P0、P1、P2、P3、待定排序。
- 现状数据可以放在这里：收录与抓取表（引擎 × 收录量 × 抓取次数 × 抓到的页面类型，收录量写明后台、统计口径、日期）。

### 4. 路线图

按级别分批，每批写清做什么、谁负责、什么时候验收。级别标准（详见 [severity.md](severity.md)）：

| 级别 | 判定标准 | 时限（经验值） |
|---|---|---|
| P0 阻断 | 核心页面整体打不开、抓不到、收不进、读不到；安全问题、人工处置；对外说法有法律风险；上线阻塞项 | 当天响应，立即排期；修好前暂停其他上线 |
| P1 严重 | 一类重要页面的收录、排名或转化明显受损，有数据证据；对外说法违反本站口径 | 本迭代内（1–2 周） |
| P2 一般 | 局部或单页问题，影响有限 | 本月或本季度，可攒一批修 |
| P3 观察 | 经验值类、证据不足或收益很小 | 记录在案，顺手改或等数据 |
| 待定 | 依赖还没定下的本站口径或负责人决定 | 单列，定下来再定级 |

每条附上能直接用的东西：清单、草稿、命令、需求单（[technical-seo.md](technical-seo.md) 第 1 节）。

- **已达标项**：没扣分、没问题的项，按事实列，不加评价。这一节让负责人知道哪些不用动，避免返工。
- **待拍板**：每项写清问题、选项、建议、理由；只问真正要负责人定的事。

### 5. 附录

- **内部检查评分**（用户要分数或要做前后对比时）：每个引擎一个分数，标出主引擎；分项打分表（维度 × 引擎，每格写扣分原因和实测值）；各类页面得分（类型、网址数、抽样数、平均分、主要扣分）；有整改预估的，并排列出现网、方案原样、预览实测、预计（上线版 / 全部完成）。开头注明：这是检查口径，不代表效果，换了评分表版本的分数不能直接比。
- **复测指标**：指标、现在、目标、怎么看、复查日期。
- **交给 seo-analytics-reporting 的效果复查清单**：每张问题卡的基线、改动日期、预期方向。
- 长清单：死链、拒绝外链、缺词表、逐页评分表，以及要提交给平台的说明草稿（如复审请求）。

## 写法

- 结论在前。一节开头先给结论，再给证据。
- 先写事实，再写判断；一个问题一张卡。
- 数字带单位、来源和日期，写清数据覆盖的范围，例如「72 字符」「正文 1,079 词（不含表格）」「重合率 79%（6 词片段，对照上级和同级页）」「GSC 只显示部分查询」。
- 核实状态分三种标清楚：「已核实」「推定」「未验证」；依据分三类标清楚：官方规则、经验值、推断。不把经验值写成规则。
- 建议写到「改什么、改成什么样」，不替开发写技术方案细节。
- 涉及对外说法的问题，注明对照的是哪一版本站口径文件。
- 不用空词（显著、大幅、全面提升），写具体变化；不写「标题不好」「内容太少」这种没有证据的判断；不把一个案例写成普遍规律。
- 不表扬自己的工作，也不迎合负责人的预期。问题照实写。
- 用户（负责人）原话定过的事，引原话，并写明日期。
- 涉及内部系统的路径、命令，可以写进给技术的附录；正文用负责人能看懂的话说。
- AI 可以把截图、导出数据整理成问题卡初稿、归类、查重；事实、定级、本站口径必须逐条核对后才进报告。

## 交付前检查（12 项）

| # | 类别 | 检查项 |
|---|---|---|
| 1 | 范围 | 写明站点、语言、页面、日期、工具和版本、抓取身份（UA、是否渲染 JS） |
| 2 | 范围 | 页面按模板分组，抽样有代表性；重点页全查 |
| 3 | 证据 | 每个问题有可复核的证据：网址、截图、导出文件，带日期 |
| 4 | 证据 | 所有数字都有来源和日期，统计口径写清楚 |
| 5 | 证据 | 官方规则、经验值、推断分别标明 |
| 6 | 判断 | 沿主线从抓取往后查，卡点有数据支撑 |
| 7 | 判断 | 先排除了季节、统计口径断点、报告故障这些假象 |
| 8 | 判断 | 每个问题都写了范围：多少页、哪类模板、哪些语言 |
| 9 | 定级 | P0–P3 都有理由，没有照搬工具的严重度 |
| 10 | 定级 | 涉及对外说法的问题，对照了最新一版本站口径文件 |
| 11 | 交付 | 每个问题都有负责人和验收方法 |
| 12 | 交付 | 摘要一页说清结论、卡点和要拍板的事 |

打不了勾的项，要么补上，要么在报告里写明原因。

## 问题卡与逐页评分表（CSV）

页面多时，附 CSV，用表格软件就能打开；复测时用同一份列名，方便逐行对比。

问题卡：

```
编号,现象,证据,范围,依据,环节,建议,级别,级别理由,负责人,批准人,验收,状态
```

逐页评分（v2 评分表）：

```
网址,页面类型,主题词,评分表版本,总分,A,B,C,D,E,F,G,H,I,J,K,L,正文词数,独有词数,主题词组密度（参考）,主题词密度（参考）,最大重合率,缺的有量词,主要问题
```
