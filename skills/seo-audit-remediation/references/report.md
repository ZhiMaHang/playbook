# 报告

每次评分交两样：

- **Markdown 报告**：存档用，放在站点工作目录；
- **HTML 看板**：给负责人看。把数据写成 JSON（字段见 [../assets/report-template.html](../assets/report-template.html) 头部注释），运行 `node scripts/build_report.mjs 数据.json 报告.html` 生成静态页。生成出来的页面不靠脚本就能显示全部内容。环境里有发布网页的工具时，默认私有发布，把链接给负责人。

两份内容要一致：先写 Markdown，再从它整理出 JSON。生成后打开看一眼，确认各节都有内容。

## 结构（按顺序）

1. **抬头**：
   - 站点和范围（多少页、哪些类型）；
   - 日期；
   - 数据来源：抓取、日志、平台、工具、代码版本；
   - 抓取用的 UA。
2. **总分**：
   - 每种口径一个分数，并标出哪个是主口径。
   - 配一句话结论：分丢在哪里。例如「页面技术底子过关，分数丢在页面以外和内容本身」。
   - 有整改预估的，并排列出四个分数：现网、方案原样、预览实测、预计（上线版 / 全部完成）。
3. **根因**：不超过 3 条。每条从现象到原因，证据链写完整。
4. **现状数据**：
   - 收录与抓取表：引擎 × 收录量 × 抓取次数 × 抓到的页面类型；
   - 或者页面的关键实测值：长度、密度、重合率、链接数。
5. **分项打分**：
   - 维度 × 口径的分数；
   - 每格的扣分原因，写实测值，不写形容词。
6. **各类页面得分**：类型、网址数、抽样数、平均分、主要扣分。
7. **关键发现**：按 P0 / P1 / P2 排。每条写三样：
   - 现象；
   - 证据：网址、截图、数据、代码位置；
   - 影响。
8. **解决方案**：
   - 分三档：P0 本周、P1 两到四周、P2 之后；
   - 每条写清四样：经办人（技术 / 运营 / 平台账号所有者）、改哪里、怎么做、验收标准；
   - 附上能直接用的东西：清单、草稿、命令。
9. **已达标项**：没扣分的项，按事实列，不加评价。这一节让负责人知道哪些不用动，避免返工。
10. **待拍板**：
    - 每项写清：问题、选项、建议、理由；
    - 删除或关闭可见内容、改定稿口号、换网址、换域名这类，各自单独成项。
11. **复测指标**：指标、现在、目标、怎么看、复查日期。
12. **数据和方法说明**：
    - 评分标准是自定的，不是搜索引擎的官方分；
    - 用到的口径：正文、密度、重合率、长度；
    - 缺了哪些数据，相关项怎么处理的；
    - 哪些数字是近似值；
    - 页面分数和排名的关系：页面分高，不等于能排上。
13. **附录**：长清单（死链、拒绝外链、缺词表、逐页评分表），以及要提交给平台的说明草稿。

## 写法

- 结论在前。一节开头先给结论，再给证据。
- 数字带单位和口径，例如「72 字符」「正文 1,079 词（不含表格）」「重合率 79%（6 词片段，对照上级和同级页）」。
- 状态分三种标清楚：「已核实」「推定」「未验证」。
- 不用空词（显著、大幅、全面提升），写具体变化。
- 不表扬自己的工作，也不迎合负责人的预期。问题照实写。
- 用户（负责人）原话定过的事，引原话，并写明日期。
- 涉及内部系统的路径、命令，可以写进给技术的附录；正文用负责人能看懂的话说。

## 逐页评分表（CSV）

页面多时，附一份 CSV，用表格软件就能打开。一页一行，列名如下：

```
网址,页面类型,主题词,总分,A,B,C,D,E,F,G,H,I,J,K,L,正文词数,独有词数,主题词组密度,核心词密度,最大重合率,缺的有量词,主要问题
```

复测时用同一份列名，方便逐行对比。
