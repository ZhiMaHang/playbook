# 制作与质检

在三步主流程的第一、二步处理 TTS、源画面、后期、封面或成片验收时读取本文件；第三步三平台发布和可选评论步骤不需要读取。主技能契约优先：第一步只整理一版完整口播并等待用户明确确认，不扩展成多候选文案提案；第二步完成正式发布包、交给用户手工发布视频号并停在 `PACKAGE_READY`。

## 1. 先做证据盘点

先确定项目根、本期目录和已有资产，不要先运行生成器：

```bash
rg --files <项目根> | rg '视频[0-9]+|成片|终版|口播|字幕|封面|workflow|task|发布物料'
git -C <仓库> status --short --branch
ffprobe -v error -show_streams -show_format -of json <已有媒体>
```

至少核对：

- 文件是否真实存在、是否非空；
- 音视频时长、画幅、帧率、编码、声道；
- 文件是源片、过程件还是终版；
- 本期用户提供的截图、录屏或示意图是否可用、对应哪段讲解；静态图实际打开检查，录屏另核对可用片段、尺寸与音轨；
- 口播稿、音频、字幕和发布物料是否属于同一版文案；
- 已有字幕源文件则核对是否完整覆盖实际口播（含第一句）、是否混入未口播的封面标题、文档标题或栏目名；没有则由本技能按锁定稿和实际音频生成，不要求用户补交字幕文件；
- 用户明确指定或当前已验收的同规格三版平台封面及其生成脚本/模板是否可作为样式基准；用户已经指出有问题的封面不得继续作为模板；
- Git 中哪些是本期新文件，哪些是用户原有修改。

用户只口头说“已经有”但没有找到文件时，状态是 `INPUT_UNVERIFIED`，不是 `SOURCE_READY`。视频编号、周编号或同名文件有冲突时，以实际目录与上一期体例消歧，不猜 `wN`。

Skill、计划、提示词、底图或后台任务说明只能证明“准备过”，不能证明音频或视频已经生成。远端任务成功也不等于本地交付文件已保存。

## 2. 文案锁定与事实边界

第一步无论收到的是完整口播、主题、图片还是原始素材，都必须先向用户展示一版将被逐字转成语音的完整文案。用户给出完整口播时保持原文并回显；只有主题或素材时整理单一完整稿，不主动提供多套候选。首次请求“做音频”或“第一步”不等于确认文案。

展示文案后状态记为 `COPY_PENDING_CONFIRMATION`，停止并等待用户明确回复“确认”“可以”“就按这版”或同等意思。确认前不得运行 TTS、生成试音或把草稿写成锁定稿。用户提出修改时，必须展示合并后的完整新版并再次等待确认；只有当前完整文本获得明确确认后才进入 `COPY_LOCKED`。锁定稿如因事实核验需要改动，也必须重新展示完整稿并再次确认。

新闻、产品功能、价格、政策、平台规则等会变化的事实必须在发布前用一手来源复核。成片钩子可以更口语，但标题、封面、简介要用问号、条件句或适用范围守住事实边界；不要把局部测试写成全面上线。

锁定稿发生修改时，以下内容会联动失效：

| 修改 | 至少需要重做或重验 |
|---|---|
| 口播文字 | TTS、字幕、口型、首尾画面、相关标题/简介/评论 |
| TTS 语速或音色 | 音频、数字人口型、字幕时间轴 |
| 剪辑点或成片时长 | 字幕时间轴、可选配乐、首尾文案、发布物料中的时长 |
| 事实口径 | 口播、标题、封面、简介、评论、来源说明 |

不要只改字幕却保留旧音频，也不要只换音轨后宣称数字人口型仍完全同步。

### 去 AI 味

本节只用于本技能起草或整理的口播。用户给出完整文案时保持原文，看到 AI 腔只作为修改建议列给用户，由用户决定改不改。

起草时避开以下写法，它们会让观众一听就觉得是 AI 写的：

1. 「不是 A，是 B」「不是……而是……」式对举纠偏；
2. 自问自答的设问、结尾反问或升华金句；
3. 排比、三连、对仗，以及每句一样长的工整节奏；
4. 句句挂「某某称」：出处要有，但合并着交代、换着说法说，能一句交代就不句句挂；
5. 公文词（注明、获准、验证、交付、口径之类），能换口语就换；
6. 冒号解释句、引号强调词；
7. 套话连接词（值得注意的是、换句话说、本质上、简单来说之类）；
8. 播音腔、营销腔和夸张情绪词。

改写后用两路互不相看的审稿（例如两个独立的子代理）：一路只挑 AI 腔并打分；一路只对照本期事实核查记录挑说过头的地方。事实核查记录放在本期过程目录，逐条写陈述、一手出处和口径限定。两路意见冲突时事实口径优先；自动修改几轮仍不收敛时，取各稿评价最好的句子手工合稿再审。

## 3. TTS

只有状态已经是 `COPY_LOCKED` 才能进入 TTS。第一步默认使用免费路线，沿用最近一期已验收的音色、语速、格式和实际目录；这些信息能从仓库查明时不追问。用户明确指定不同音色、语速、服务或目录时才覆盖默认值。完成本节的音频生成与自动核验后，按 [work-ledger.md](work-ledger.md) 的 Git 章节自动提交本期文件并推送，核对远端后交付；不启动视频生成。

可复用同插件脚本：

```bash
PLAYBOOK_ROOT="${CLAUDE_PLUGIN_ROOT:-<playbook仓库根>}"
DHV_ROOT="$PLAYBOOK_ROOT/skills/digital-human-video"
```

不要假设默认 `python3` 已安装 `edge_tts`。先探测可用解释器：

```bash
python3 -c 'import edge_tts' 2>/dev/null || <候选解释器> -c 'import edge_tts'
```

复用 `compose.sh`、`make_card.sh` 等内部调用 `python3` 的 shell helper 时，先让已验证解释器所在目录排在 `PATH` 前面；不要把某台机器的 Anaconda 绝对路径写死进 Skill 或脚本：

```bash
DHV_PYTHON_BIN="<已验证解释器的绝对路径>"
PATH="$(dirname "$DHV_PYTHON_BIN"):$PATH" "$DHV_ROOT/scripts/compose.sh" <过程目录> <输出.mp4>
```

选择免费 edge-tts 时显式清空可能触发其他供应商的变量，并显式指定语速、音色：

```bash
env TTS_APPID='' TTS_TOKEN='' TTS_RATE='+20%' EDGE_VOICE='zh-CN-XiaoxiaoNeural' \
  <已验证的python> "$DHV_ROOT/scripts/tts.py" --script <用户已确认的定稿.md> --outdir <过程目录/audio>
```

参数是本期输入，不把旧环境值当成默认事实。不要把 API Key、Token 或账号信息写进台账、日志摘要和 Git。

生成后逐个检查：

```bash
ffprobe -v error -show_entries format=duration -show_entries stream=codec_name,sample_rate,channels \
  -of default=noprint_wrappers=1 <音频>
```

自动核验至少包括：TTS 输入与确认稿逐字一致、MP3/WAV 完整解码通过、时长与编码/采样率/声道有实测记录。通过后记 `AUDIO_AUTO_QA_PASS`。

几点实测经验：

- edge-tts 会随服务端校验升级而失效（实测一例：7.2.8 握手被拒、返回 403，升到 7.3.1 恢复）。`tts.py` 遇到这种失败不会报错，而是退到 macOS `say`，每个降级的段落在 stderr 各打一行“edge-tts 两次均失败,降级 macOS say”；出现“降级 macOS say”这句即判 TTS 失败、丢弃产物（stdout 里的“引擎=edge-tts(降级)”是正常输出，不算）。安装或升级 edge-tts 前先说明包名、版本和来源，取得用户同意，在临时虚拟环境里装指定版本、记进本期文件，不改用户的全局环境。
- 要词级时间戳时用 Python API：在同一次 `edge_tts.Communicate(text, voice, rate=…, boundary="WordBoundary").stream()` 里同时写音频、收集 WordBoundary 事件（offset、duration 以 100 纳秒为单位）另存一份。`tts.py` 和 `python -m edge_tts` 命令行不输出词级时间戳；另起一次合成拿到的时间戳不能保证对得上实际用的那份音频；分段合成时按段累加偏移。字幕分屏和镜头切点直接用词级起点计算，一个词元横跨分屏点时按词长内插，比事后用静音检测找停顿更准。
- 时长估算用最近一期同音色、同语速的实测字速；短句多、停顿多的稿子会更慢。估算与实测相差明显时，如实告诉用户，不擅自删句。
- 用户要换音色时，在 `COPY_LOCKED` 之后，用锁定稿开头一段生成 4–5 种候选试听样（含现用音色作对照），用户选定后再生成全片；换音色后字幕和镜头时间轴都按新配音的词级时间戳重排。

还要实际听首句、专有名词、数字和末句，完成后记 `AUDIO_VERIFIED`。当前工具无法接收音频时，使用可用的本地无提示词 ASR 辅助核对并如实记录“试听待完成”，不能将转写冒充试听，也不因此等待额外 Git 授权或跳过自动推送；若核验发现漏词、截断或文件损坏，则先修复重验。数字人引擎单段有时长上限时按语义拆段，不删文案；以实测音频时长为准，不用字数估算替代。

## 4. 源画面路由

按已有证据选一条，不要混用：

### 已有原始 MP4

直接检查时长、音轨、口型、画幅和可用剪点，进入后期。先确认源片是否已经带背景音乐、字幕或角标；新期不得从带禁用曲目的旧源片直接继承音轨。

如果同时存在 MP4 内嵌音轨和独立“定稿音频”，先确定权威关系：

1. 对比两者时长、波形/试听、首末句和关键字；
2. 数字人口型由哪一份音频驱动，就把哪一份视为同步基准；
3. 独立音频不同于同步基准时，不直接替换后宣称同步。在本技能的第二步中保留诊断并停止，不自动重生画面；如用户另行明确授权重生，则退出当前第二步，把重生作为新的制作任务处理；
4. 没有用户确认的逐字稿时，可先转写为字幕草稿，但必须复核专有名词、数字和标点，确认后才烧录。

### 用户本机 ComfyUI 或其他本地工作流

默认用户在自己的PC上用ComfyUI将每镜头人物图与对应WAV生成口播视频；镜头ID、素材包和返回规范见 [storyboard-motion.md](storyboard-motion.md)。不根据旧记录假定用户当前模型、显卡、节点、分辨率或时长上限。把用户返回的逐镜头MP4按ID当稳定源片验收。工作流成功截图不是交付物；必须拿到本地MP4并逐一 `ffprobe`。源片短于定稿音频、口型明显错位或末句被截断时，停止后期并要求重生成或由用户明确接受替代方案，不能用长时间尾帧定格掩盖。

### 需要重新生成数字人 / 视频

本技能的第二步不包含任何计费重生，也不进入即梦或其他视频生成路线。源片失败且只能靠重生解决时，记录失败证据并停止。只有用户另行明确授权后，才退出当前第二步，完整读取同插件 `skills/digital-human-video/SKILL.md`，把重生作为新的制作任务处理；其文案、肖像、图片、分镜和成本确认门全部生效。

输出画幅由 `ffprobe` 决定，不写死服务端规格。只换音轨是有口型风险的降级方案，必须明示，不能为了继续第二步而静默采用。

### 实拍素材＋图卡（无人物出镜）

适用条件、路线选择、素材下载同意与权利记录、来源标注和状态映射都以 [storyboard-motion.md 第 7 节](storyboard-motion.md#7-实拍素材图卡路线无人物出镜) 为准。画面由真实来源的实拍片段、截图与本技能制作的图卡组成，由本技能直接合成，不经过 PC ComfyUI。

### 纯图卡 / 无数字人

只有用户选择这一方向时使用。文字型框架图用代码绘制，保证中文字和顺序可控；不要用图像生成模型承载关键中文清单。

## 5. 后期制作

保留一个稳定源片与一份可复现的剪辑参数，终版始终从稳定源重新生成，避免多代转码。

本系列默认采用 [storyboard-motion.md](storyboard-motion.md) 的人物口播＋辅助素材＋特效字幕模板：Image 2.5人物分镜图与对应配音交给用户的PC ComfyUI生成视频；用户每期另提供一份截图、录屏或示意图，三选一即可。本技能接回源片后按讲解语义插入素材，统一完整字幕、关键词高亮与适量轻动效；保留锁定口播与同步基准。用户的当期要求覆盖默认。

辅助素材作为后期画面插入，不需要做成 ComfyUI 人物镜头，也不取代口播源片验收。缺素材时可继续准备与核验已有内容，但除用户明确本期不用素材外，不得把纯口播版标成 `FINAL_QA_PASS`、`PREVIEW_READY` 或 `PACKAGE_READY`；不擅自下载或生成一份无关素材补数。

### 剪辑

- “剪掉一秒”先找语义停顿、静音和可接受画面，再确定保留区间；不要盲目连续使用 `-t 当前时长-1`。
- 可用 `silencedetect=noise=-40dB:d=0.20`、`blackdetect` 或 `freezedetect` 辅助定位候选区间；这些阈值只是诊断起点，不能自动决定语义剪点。末句之后保留多少余量以试听和画面收口为准。
- 多段保留区间要记录在过程目录或本期台账中，方便重建。
- 改剪点后重排字幕、可选配乐、角标和首尾验收；不能沿用旧时间轴。
- 结尾必须完整说完锁定稿的末句，不能只看总时长。

### 辅助素材插入

- 选择与口播直接对应的区间；截图保留必要上下文并框选/放大重点，录屏截取所讲操作，示意图按讲解顺序高亮。一份素材可按语义分段使用，无需三类齐备或每句切画面。
- 默认替换对应时段的画面，主音轨和总时长不变；全屏或人物画中画以素材可读性为准。录屏原声默认静音，不与口播叠加；返回人物时继续原有同步时间轴。
- 保存原素材与本期副本、来源说明、素材ID、口播对应关系、实际插入区间、录屏源区间、裁切/布局及标注参数；详细字段见分镜模板。字幕与 AI 角标在辅助画面上继续显示，避开素材重点。

### 特效字幕与 AI 标识

- 用户说“用默认的特效风格”或未指定样式时，直接采用本节默认。字幕由本技能从锁定稿与实际音频制作；用户无需提供 SRT/ASS 或样式参考，已有字幕文件则先核对再复用。第二步的交付说明与口令见主技能“用户交付与默认特效风格口令”。
- 字幕按最终音频/剪辑时间轴烧录；检查安全区、标点行首、断词和人物嘴部遮挡。
- 标题元数据与字幕分开：字幕必须覆盖锁定口播的全部实际发声，包括第一句；如果第一句口播与本期标题或封面钩子文字重合，仍按口播正常进入字幕源文件并烧录。不得把没有实际口播的封面标题、文档标题、栏目名或标签额外混入字幕。
- 每期在完整字幕基础上做特效字幕：按发声时机高亮关键原词，可在重要数字或结论处加单次轻微放大/淡入。避免逐字弹跳、闪白和频繁音效；不以少量大字替代完整口播字幕，不添加未口播的新结论。
- 显式 AI 角标烧进成片；平台发布页的 AI 声明是另一道标识，不能二选一。
- 角标基线（按 GB 45438-2025 图解所列数值自设）：措辞取 `digital-human-video/scripts/aigc_meta.py` 的 `BADGE_TEXT`（现为「视频由 AI 生成」），同时含「AI／人工智能」和「生成／合成」两要素；字号和整行墨迹高都不低于成片最短边的 5%；从第 0 帧起全程显示，默认右上角，边距按最短边比例。
- 按成片**实际分辨率**调用 `render_text.badge(out, width=W, height=H)`（命令行 `render_text.py badge <out.png> <W> <H>`），叠在它写出的 `<out.png>.json` 给的 `x:y` 上，全程显示；不写死字号，也不写死 `overlay=W-w-40:60`。验收把这份 JSON 传给 `verify_package.py --badge-spec`。
- 可复用 `digital-human-video/scripts/render_text.py` 与 `compose.sh` 的字幕、角标和画幅处理逻辑；若是单条现成 MP4，可按同样样式建立本期专用 ffmpeg 滤镜，但必须把命令或参数留在过程目录。
- 字幕字体、字号、每行长度、安全区沿用当前仓库脚本和上一期终版这一可验证单一来源，不从记忆重写；角标文字、尺寸和位置只以 `aigc_meta.py` 与 `render_text.badge()` 为准，不沿用旧期脚本里的写法。任何改版先在台账记录。
- 退役措辞登记（除本表和 `aigc_meta.py` 的 `RETIRED_BADGE_TEXTS` 外，角标、字幕、文档都不许再用）：

| 措辞 | 状态 |
|---|---|
| 视频由 AI 制作 | ⛔ 已退役，不许再用（缺「生成／合成」要素） |
| 内容由 AI 制作 | ⛔ 已退役，不许再用（缺「生成／合成」要素） |

### 成片元数据

- 成片**保留源片的全部元数据**，包括服务商写入的 `AIGC` 等隐式标识，以及 ComfyUI 原始输出自带的 `workflow`／`prompt`；只另写一条 `description` 普通说明（`aigc_meta.AI_DESCRIPTION`）。
- 我方不是生成合成服务提供者：⛔ 不写 `AIGC`、`ContentProducer`、`ProduceID` 这类形似服务商隐式标识的键。源片原有的这些键原样保留，不删、不改。
- ⛔ 禁用 `-map_metadata -1`（它会清空源元数据）。从旧期复制脚本时，先删掉 `-map_metadata -1` 和写死的 `overlay=W-w-40:60`，再按下面的写法改。
- 编码命令追加 `aigc_meta.ffmpeg_args(源片, 源片输入序号)` 返回的参数：映射源片元数据、清掉会被写成重复值的 brand 三键、写说明字段、`+faststart+use_metadata_tags`。输入序号必须显式给：不写时 ffmpeg 取第 0 路的元数据，源片不在第 0 路就整套丢光。
- 源片已有 `description` 时 `ffmpeg_args` 直接报错、不覆盖，交人处理；只有它恰好就是我方说明字段（对已出的成片再混音、再封装）时照写一遍，不算覆盖。
- `workflow`／`prompt` 键可能带工作流、模型文件名和提示词：按原样保留，`verify_package.py` 只报 WARN 提示，发不发由人决定。
- 多段拼接时一个文件只留一份隐式标识：容器保留第一段源文件的元数据，全部片段的元数据写进本地 `<终版.mp4>.source-metadata.json`（不上传）。`compose.sh` 自动做这一步；逐镜头源片在本技能里拼接时，`ffmpeg_args` 和验收的 `--source` 都用第一个镜头的源文件，再跑 `python3 <playbook 仓根>/skills/digital-human-video/scripts/aigc_meta.py sidecar <终版.mp4>.source-metadata.json <镜头1.mp4> <镜头2.mp4> …`，各镜头不同时它打印 ⚠️。单条完整源片就用它本身。
- 带 `use_metadata_tags` 后所有键都写进 mdta `keys` 盒，只认 iTunes 风格 `©nam`、`desc` 的读取器读不到标题和说明，这是已知取舍；ffprobe 两种都能读。`creation_time` 同时写在 mvhd 和 mdta 里，ffprobe 会读成「mvhd 值;mdta 原串」。普通源片照常映射即可；源片本身已读成带「;」的形式（它也是带 `use_metadata_tags` 写的）时，`ffmpeg_args` 显式写回一个值（否则 mvhd 的创建时间会被写成 0）：mdta 原串是带时区的绝对时间就写它，不是（如 ComfyUI 的 VHS 保存节点写的 `now`、不带时区的本地时间）就写已归一成 UTC 的 mvhd 那半。`compare` 比这个键时，源片原串是绝对时间就要求终版原串逐字相同，否则比两边能解析的时刻（精确到秒）。

示例（路径都是占位符）：

```python
import importlib.util
from pathlib import Path

PLAYBOOK = Path("<playbook 仓根>")
spec = importlib.util.spec_from_file_location(
    "aigc_meta", PLAYBOOK / "skills/digital-human-video/scripts/aigc_meta.py")
aigc_meta = importlib.util.module_from_spec(spec)
spec.loader.exec_module(aigc_meta)

src = "<源片.mp4>"                              # 本条命令的第 0 路输入
cmd = ["ffmpeg", "-y", "-i", src, "-i", "<配音.wav>",
       # …滤镜、-map、编码参数…
       *aigc_meta.ffmpeg_args(src, 0),           # 保留源元数据 + 说明字段 + brand 三键清理
       "<终版.mp4>"]
```

实拍素材＋图卡路线没有 AI 生成源片，本路线的 AI 成分是锁定配音。编码参数用 `aigc_meta.ffmpeg_args(<锁定配音.wav>, <它的输入序号>)`，验收的 `--source` 也传这份 WAV；终版音频不是直接取这份 WAV（例如取了处理过的副本或混音结果）时，额外加一路 `-i <锁定配音.wav>`，只用来带元数据、不 `-map` 它的流。这样实拍片段里第三方的 `title`、`copyright`、位置、机型等键都不会进成片。实拍片段本身也是终版命令的输入，所以画面和音频都要显式 `-map`（画面取合成结果，音频取锁定配音或以它为主的混音结果）：实测整条命令一个 `-map` 都不写时，ffmpeg 自动选了声道最多的音频，也就是实拍片段的立体声原声；只写了画面的 `-map`、漏写音频时，成片没有音轨。终版命令一律加 `-map_chapters -1`（这不是被禁的 `-map_metadata -1`）：实测不加时，实拍片段自带的章节和一条数据轨被带进了成片。锁定配音 WAV 带 `description` 时 `ffmpeg_args` 会报错，交人处理。实拍片段不是 AI 源片，不必跑上面的 sidecar。下载素材时不加 yt-dlp 的 `--embed-metadata`／`--add-metadata`。注意：ffmpeg 不写 `-map_metadata` 时，默认会拷第 0 路输入的全局元数据（但会丢掉 `creation_time`），所以不能把“不映射”当成没有元数据；也不要为了凑参数伪造源片。

出片后可单独核一次：`python3 <playbook 仓根>/skills/digital-human-video/scripts/aigc_meta.py check <终版.mp4> --source <源片.mp4>`。

### BGM 与响度

后续新期默认不加 BGM，只用锁定口播主音轨。曾在任一平台收到版权处置（认领、限播、禁播或下架）的音源，连同它改名或复制的同源音频，一律禁用。旧期脚本中的音乐路径、音量、`amix` 链和归档说明里的“系列共用配乐”只作历史记录，不能成为新期默认；复制旧脚本时先移除这些旧配乐输入与参数。不要为替换禁用曲目而自动换另一首音乐。

禁用清单（每条写文件名、SHA-256 和处置情况）由使用方维护在本地覆盖文件里，不写进本仓。**推荐放 `~/.config/zmh-short-video-pipeline/bgm-blocklist.local.md`**：技能目录 `references/` 下的 `*.local.md` 被 .gitignore 挡在版本库外，装成插件后读不到，换版本升级时也会丢。本技能目录的 `references/bgm-blocklist.local.md` 只作从仓库工作区直接运行时的后备（别放到技能目录的别处，那里不在排除规则内）；两处按这个先后取第一个存在的，都不进版本库。两处都找不到清单时，不能当成没有禁用曲目：加音乐、核对旧音轨残留、判断某个音源是不是禁用曲目之前，先向用户确认有没有禁用曲目、清单在哪。

用户另行指定新音乐时，先核对音源、商业使用和视频号／抖音／B站／YouTube 使用范围，记录权利依据；没有可复核依据就保持无 BGM。通过权利核对也不等于平台 Content ID 一定放行，平台检查按实际结果记录。仅在本期明确获准加入新音乐后，才按以下混音原则处理：

- 先确认源片没有重复音乐，且新音源与禁用清单内的曲目不相同；
- 人声持续的短视频配乐保持低音量，不做持续泵动的侧链；
- `amix` 使用 `normalize=0`；两遍 `loudnorm`，第二遍使用 `linear=true`；
- 项目没有其他口径时以约 `-14 LUFS` 为目标，最终以实际听感和平台要求为准；
- 配乐可闻但不盖人声，尤其检查手机敏感的 1–4 kHz。

没有 BGM 时仍核验完整人声、首尾、响度与真峰值；不得为匹配历史版本的人声／配乐平衡而把禁用音源混回。

## 6. 三版平台封面

本节用于第二步正式发布包分支。用户明确只做预览时跳过本节；需要转为正式发布包时，再回到第二步制作平台封面并完成 QA。

默认交付：

| 用途 | 尺寸 | 文件名 |
|---|---:|---|
| 视频号 / 抖音竖封面 | 1080×1440（3:4） | `封面.png` |
| B站横封面 | 1440×1080（4:3） | `封面-横4x3.png` |
| YouTube Shorts 封面 | 1080×1920（9:16） | `封面-youtube-shorts.png` |

优先使用原始底图或没有字幕/角标的干净源帧。横版要重新构图；B站 4:3 即使只有竖版源图，也使用当前左文右像模板，不以竖图居中加两侧模糊柱代替。其他横版规格只有缺少宽图且没有已验收重构模板时，才可使用模糊延展保住完整竖版前景。不要直接把竖版裁成横版导致切脸或切字。

封面样式以“用户明确指定或当前已验收的同规格封面及其生成脚本/模板”为单一基准。用户已经指出有问题的封面立即退出候选基准。允许变化的只有底图、适配构图和本期标题文案；标题区的黑底/遮罩、字体、字重、颜色、描边、行距、对齐和相对位置必须保持同一模板。黑底或遮罩是标题样式的一部分，不能因更换底图或重新构图而丢失。

智码航当前 3:4 竖封面统一基准为视频 6、7：标题块居中并保留深色黑底带，沿用相同字体、字重、颜色、描边、行距和相对位置；可以替换底图与本期文案，但不能把黑底带去掉或换成另一套标题样式。

智码航当前 B站 4:3 统一基准为视频 6、7：1440×1080，左侧近黑标题区、右侧人物区并柔和过渡；金色圆角标签，第一行金色、第二行白色、深色描边；标题左对齐并按像素自动缩小，人物与文字不重叠。不得退回竖图居中加两侧模糊柱，或人物居中叠全幅大字的旧布局。

视频 1–4 的 B站 4:3 封面已按视频 6、7 的统一模板重制，本地替换文件不能自动证明平台公开页已经更新。处理这类已发布旧视频时，保留原封面与发布状态的历史记录，把新文件标为“待用户上传/待替换”；只有从公开页核验新封面后才能记为“已更新”。

YouTube Shorts 独立的 9:16 `封面-youtube-shorts.png` 必须在第二步生成、归档，第三步发布 YouTube 时上传。标题块应放在画面中部偏左，避开右侧操作列与底部标题/频道信息区；不得直接复用可能在 Shorts 界面溢出或被遮挡的 3:4 封面。普通 YouTube 16:9 专用图不生成。

实拍素材＋图卡路线（无人物）沿用同一封面模板：B站 4:3 仍是左文右像，「右侧人物区」读作「右侧主体区」，主体落在模板的图像分区里；三版封面角上可加一行来源标注（例如「实拍来源：<发布方>官方」），位置避开标题区和平台遮挡区，这是本路线允许的唯一新增元素。

封面检查：

- 缩略图尺寸下仍能读；
- 最多两三行核心文字，避免整段文案；
- 人脸不被文字盖住；
- 3:4、4:3、9:16 三个规格都保住完整钩子；B站 4:3 版还要核对左文右像结构、黑底和缩略可读性，Shorts 9:16 版还要核对右侧和底部安全区；
- 封面事实口径与定稿一致，但不要求逐字复制口播。

## 7. 成片与包验收

先运行本 Skill 的源文件保护型校验脚本：

```bash
python3 scripts/verify_package.py \
  --video <终版.mp4> \
  --badge-spec <角标.png.json> \
  --source <源片.mp4> \
  --cover-vertical <封面.png> \
  --cover-bilibili <封面-横4x3.png> \
  --cover-youtube-shorts <封面-youtube-shorts.png> \
  --max-duration <目标上限秒数> \
  --target-lufs -14 --lufs-tolerance 2 \
  --frames-dir <临时抽帧目录>
```

用户选择预览覆盖时，只验证视频，不传三版平台封面参数：

```bash
python3 scripts/verify_package.py \
  --video <预览终版.mp4> \
  --badge-spec <角标.png.json> \
  --source <源片.mp4> \
  --max-duration <目标上限秒数> \
  --target-lufs -14 --lufs-tolerance 2
```

脚本不修改源视频或封面，但 `--frames-dir` 会创建/覆盖抽帧，`--json-out` 会写报告；严格只读审计时省略这两个参数。默认的 1080×1920、H.264/AAC 与三版平台封面尺寸是智码航当前交付规格；项目规格不同时显式传参或只做对应检查。脚本能机检角标尺寸（几何 JSON 与角标 PNG 实测字高都要达标）、位置、全程出现（取第 0 帧、此后每个整秒时刻屏上的那一帧、末帧逐一比对像素；MP4 顶层 box 声明的长度超出文件即判截断，少 1 个字节也算；盒结构完整但内容损坏、解码器报错的同样判 FAIL，解码器没报错的损坏查不出；不是 MP4/MOV 或末尾 box 没声明长度时只报 WARN「截断无从核对」）和措辞常量，以及源元数据保留和说明字段，**不能 OCR**；缺 `--badge-spec` 或 `--source` 直接 FAIL（「AI 角标未机检」「源元数据保留未核」）。只读审计已发布旧片时加 `--legacy-audit`，这几项降为 WARN，不能据此写 `FINAL_QA_PASS`。脚本不能识别字幕语义、辅助素材是否匹配讲解、字幕动效是否合适、版权或口型，这些项目必须实际观看核对。

人工必须完成：

1. 播放首句、末句和每个剪点；
2. 每个分镜至少看一帧，检查字幕、角标、遮挡和画面顺序；重点检查 0 秒和第一个字幕切点，确认第一句实际口播从开头即有对应字幕；
3. 对照锁定稿逐字核对全部字幕、首尾与关键数字，并确认没有混入未口播的封面标题、文档标题、栏目名或标签；
4. 检查辅助素材实际入片且与讲解对应，所用区间头尾与重点均实际观看，文字/操作在手机画幅下可读，字幕和角标不遮挡重点；核对关键词高亮与轻动效时机；用户明确本期不用辅助素材时记录原因；
5. 检查嘴型与音轨，无明显漂移，辅助画面插入前后口播连续且录屏原声没有意外叠入；
6. 确认新期没有禁用曲目或旧音轨残留、人声清晰且响度合适；若本期另获准使用新音乐，再检查配乐稳定、可闻且不压人声；
7. 第二步正式发布包分支把本期 3:4、4:3、Shorts 9:16 分别与用户指定或当前已验收的同规格基准并排查看；原尺寸和缩略图都要核对标题区黑底/遮罩、字体、字重、颜色、描边、行距、对齐和相对位置；B站 4:3 版额外确认左文右像、标题不越过人物分区且不存在竖向模糊柱；Shorts 9:16 版额外确认标题不进入右侧操作列和底部信息区；预览分支跳过；
8. 运行一次完整解码，确认解码器全程没有报错：上面带 `--target-lufs` 的命令已包含这一步，不测响度时改用 `--decode-check`。解码器不报错的损坏这一步查不出，画面与声音仍以前面几项的实际观看、监听为准。

角标位置的已知局限：默认右上角（1080×1920 时框在 x 574–1040、y 60–154）落在各平台手机播放界面的顶部一带。按公开资料推断——没有做真机截图验证——抖音、视频号、B站、YouTube Shorts 上，系统状态栏和平台顶栏的图标可能压住角标的上沿或右端，长屏手机把 9:16 画面放大铺满时右端还可能被裁掉几十像素。当前接受这一点、位置不动；人工核对「首帧角标不被平台界面遮挡」时，按「主体文字仍看得清」判断。要换位置就改 `render_text.badge()` 的 `anchor` 或边距比例，并先用手机截图核过再发。

任何一项失败，状态仍是 `SOURCE_READY` 或“后期处理中”，不能写 `FINAL_QA_PASS`。

正式发布包通过验收并完成本期归档后，按 [work-ledger.md](work-ledger.md) 的 Git 章节自动提交成片、三版封面、平台物料及必要的制作/QA 记录，推送并核对远端提交，再交付并停在 `PACKAGE_READY`。预览分支只处理过程目录中的预览与 QA；用户本轮明确要求只生成本地、不提交或不推送时按其限制执行。Git 完成不授权上传平台。
