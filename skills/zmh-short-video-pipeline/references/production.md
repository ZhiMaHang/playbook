# 制作与质检

在两步流水线的 TTS、源画面、后期、封面或成片验收阶段读取本文件。主技能的两步契约优先：第一步不重新做选题或文案提案，第二步质检通过后不无故停在发布确认。

## 1. 先做证据盘点

先确定项目根、本期目录和已有资产，不要先运行生成器：

```bash
rg --files <项目根> | rg '视频[0-9]+|成片|终版|口播|字幕|封面|workflow|task|发布物料'
git -C <仓库> status --short --branch
ffprobe -v error -show_streams -show_format -of json <已有媒体>
```

至少核对：

- 文件是否真实存在、是否非空；
- 音视频时长、画幅、帧率、编码、声道；
- 文件是源片、过程件还是终版；
- 口播稿、音频、字幕和发布物料是否属于同一版文案；
- 字幕源文件是否完整覆盖实际口播（含第一句），以及是否误把未口播的封面标题、文档标题或栏目名写成字幕；
- 用户明确指定或当前已验收的同规格两版平台封面及其生成脚本/模板是否可作为样式基准；用户已经指出有问题的封面不得继续作为模板；
- Git 中哪些是本期新文件，哪些是用户原有修改。

用户只口头说“已经有”但没有找到文件时，状态是 `INPUT_UNVERIFIED`，不是 `SOURCE_READY`。视频编号、周编号或同名文件有冲突时，以实际目录与上一期体例消歧，不猜 `wN`。

Skill、计划、提示词、底图或后台任务说明只能证明“准备过”，不能证明音频或视频已经生成。远端任务成功也不等于本地交付文件已保存。

## 2. 文案锁定与事实边界

本技能第一步由用户直接提供口播文案，该文本收到即为锁定稿；不要重新选题、提供候选或要求再确认。只有用户明确要求优化文案时，才进入文案修改，并在修改完成后重新锁定。

新闻、产品功能、价格、政策、平台规则等会变化的事实必须在发布前用一手来源复核。成片钩子可以更口语，但标题、封面、简介要用问号、条件句或适用范围守住事实边界；不要把局部测试写成全面上线。

锁定稿发生修改时，以下内容会联动失效：

| 修改 | 至少需要重做或重验 |
|---|---|
| 口播文字 | TTS、字幕、口型、首尾画面、相关标题/简介/评论 |
| TTS 语速或音色 | 音频、数字人口型、字幕时间轴 |
| 剪辑点或成片时长 | 字幕时间轴、BGM、首尾文案、发布物料中的时长 |
| 事实口径 | 口播、标题、封面、简介、评论、来源说明 |

不要只改字幕却保留旧音频，也不要只换音轨后宣称数字人口型仍完全同步。

## 3. TTS

第一步默认使用免费路线，沿用最近一期已验收的音色、语速、格式和实际目录；这些信息能从仓库查明时不追问。用户明确指定不同音色、语速、服务或目录时才覆盖默认值。完成本节后停止，不启动视频生成。

可复用同插件脚本：

```bash
PLAYBOOK_ROOT="${CLAUDE_PLUGIN_ROOT:-<playbook仓库根>}"
DHV_ROOT="$PLAYBOOK_ROOT/skills/digital-human-video"
```

不要假设默认 `python3` 已安装 `edge_tts`。先探测可用解释器：

```bash
python3 -c 'import edge_tts' 2>/dev/null || <候选解释器> -c 'import edge_tts'
```

复用 `compose.sh`、`make_card.sh` 等内部调用 `python3` 的 shell helper 时，先让已验证解释器所在目录排在 `PATH` 前面；不要把某台机器的 Anaconda 绝对路径写死进 Skill 或脚本：

```bash
DHV_PYTHON_BIN="<已验证解释器的绝对路径>"
PATH="$(dirname "$DHV_PYTHON_BIN"):$PATH" "$DHV_ROOT/scripts/compose.sh" <过程目录> <输出.mp4>
```

选择免费 edge-tts 时显式清空可能触发其他供应商的变量，并显式指定语速、音色：

```bash
env TTS_APPID='' TTS_TOKEN='' TTS_RATE='+20%' EDGE_VOICE='zh-CN-XiaoxiaoNeural' \
  <已验证的python> "$DHV_ROOT/scripts/tts.py" --script <定稿.md> --outdir <过程目录/audio>
```

参数是本期输入，不把旧环境值当成默认事实。不要把 API Key、Token 或账号信息写进台账、日志摘要和 Git。

生成后逐个检查：

```bash
ffprobe -v error -show_entries format=duration -show_entries stream=codec_name,sample_rate,channels \
  -of default=noprint_wrappers=1 <音频>
```

还要实际听首句、专有名词、数字和末句。数字人引擎单段有时长上限时按语义拆段，不删文案；以实测音频时长为准，不用字数估算替代。

## 4. 源画面路由

按已有证据选一条，不要混用：

### 已有原始 MP4

直接检查时长、音轨、口型、画幅和可用剪点，进入后期。先确认源片是否已经带 BGM、字幕或角标，避免重复叠加。

如果同时存在 MP4 内嵌音轨和独立“定稿音频”，先确定权威关系：

1. 对比两者时长、波形/试听、首末句和关键字；
2. 数字人口型由哪一份音频驱动，就把哪一份视为同步基准；
3. 独立音频不同于同步基准时，不直接替换后宣称同步。在本两步技能的第二步中保留诊断并停止，不自动重生画面；如用户另行明确授权重生，则退出当前第二步，把重生作为新的制作任务处理；
4. 没有用户确认的逐字稿时，可先转写为字幕草稿，但必须复核专有名词、数字和标点，确认后才烧录。

### 用户本机 ComfyUI 或其他本地工作流

把用户返回的 MP4 当源片验收。工作流成功截图不是交付物；必须拿到本地 MP4 并 `ffprobe`。源片短于定稿音频、口型明显错位或末句被截断时，停止后期并要求重生成或由用户明确接受替代方案，不能用长时间尾帧定格掩盖。

### 需要重新生成数字人 / 视频

本两步技能的第二步不包含任何计费重生，也不进入即梦或其他视频生成路线。源片失败且只能靠重生解决时，记录失败证据并停止。只有用户另行明确授权后，才退出当前第二步，完整读取同插件 `skills/digital-human-video/SKILL.md`，把重生作为新的制作任务处理；其文案、肖像、图片、分镜和成本确认门全部生效。

输出画幅由 `ffprobe` 决定，不写死服务端规格。只换音轨是有口型风险的降级方案，必须明示，不能为了继续第二步而静默采用。

### 纯图卡 / 无数字人

只有用户选择这一方向时使用。文字型框架图用代码绘制，保证中文字和顺序可控；不要用图像生成模型承载关键中文清单。

## 5. 后期制作

保留一个稳定源片与一份可复现的剪辑参数，终版始终从稳定源重新生成，避免多代转码。

### 剪辑

- “剪掉一秒”先找语义停顿、静音和可接受画面，再确定保留区间；不要盲目连续使用 `-t 当前时长-1`。
- 可用 `silencedetect=noise=-40dB:d=0.20`、`blackdetect` 或 `freezedetect` 辅助定位候选区间；这些阈值只是诊断起点，不能自动决定语义剪点。末句之后保留多少余量以试听和画面收口为准。
- 多段保留区间要记录在过程目录或本期台账中，方便重建。
- 改剪点后重排字幕、BGM、角标和首尾验收；不能沿用旧时间轴。
- 结尾必须完整说完锁定稿的末句，不能只看总时长。

### 字幕与 AI 标识

- 字幕按最终音频/剪辑时间轴烧录；检查安全区、标点行首、断词和人物嘴部遮挡。
- 标题元数据与字幕分开：字幕必须覆盖锁定口播的全部实际发声，包括第一句；如果第一句口播与本期标题或封面钩子文字重合，仍按口播正常进入字幕源文件并烧录。不得把没有实际口播的封面标题、文档标题、栏目名或标签额外混入字幕。
- 显式 AI 角标烧进成片；平台发布页的 AI 声明是另一道标识，不能二选一。
- 可复用 `digital-human-video/scripts/render_text.py` 与 `compose.sh` 的字幕、角标和画幅处理逻辑；若是单条现成 MP4，可按同样样式建立本期专用 ffmpeg 滤镜，但必须把命令或参数留在过程目录。
- 字幕字体、字号、每行长度、安全区，以及角标文字、位置、尺寸和持续时间，沿用当前仓库脚本和上一期终版这一可验证单一来源，不从记忆重写。项目当前脚本若显示“视频由 AI 制作”，就保持一致；任何改版先在台账记录。

### BGM 与响度

默认使用自制或明确可商用的 BGM；同插件 `make_bgm.py` 可生成零版权依赖素材。用户指定外部音乐时，先确认其有权用于目标平台并在台账记录来源，不自行推断授权。

混音原则：

- 先确认源片没有重复 BGM；
- 人声持续的短视频默认恒定低音量，不做持续泵动的侧链；
- `amix` 使用 `normalize=0`；
- 两遍 `loudnorm`，第二遍使用 `linear=true`；
- 项目没有其他口径时以约 `-14 LUFS` 为目标，最终以实际听感和平台要求为准；
- BGM 可闻但不盖人声，尤其检查手机敏感的 1–4 kHz。

智码航既有系列常用 `volume=0.09`，这是该系列的历史起点，不是所有音乐的通用正确值。

## 6. 两版平台封面

本节用于默认直接上架分支和“先别发布”的本地发布包分支。用户明确只做预览时跳过本节，收到新的发布包或发布指令后再制作平台封面。

默认交付：

| 用途 | 尺寸 | 文件名 |
|---|---:|---|
| 视频号 / 抖音竖封面 | 1080×1440（3:4） | `封面.png` |
| B站横封面 | 1440×1080（4:3） | `封面-横4x3.png` |

优先使用原始底图或没有字幕/角标的干净源帧。横版要重新构图；B站 4:3 即使只有竖版源图，也使用当前左文右像模板，不以竖图居中加两侧模糊柱代替。其他横版规格只有缺少宽图且没有已验收重构模板时，才可使用模糊延展保住完整竖版前景。不要直接把竖版裁成横版导致切脸或切字。

封面样式以“用户明确指定或当前已验收的同规格封面及其生成脚本/模板”为单一基准。用户已经指出有问题的封面立即退出候选基准。允许变化的只有底图、适配构图和本期标题文案；标题区的黑底/遮罩、字体、字重、颜色、描边、行距、对齐和相对位置必须保持同一模板。黑底或遮罩是标题样式的一部分，不能因更换底图或重新构图而丢失。

智码航当前 3:4 竖封面统一基准为视频 6、7：标题块居中并保留深色黑底带，沿用相同字体、字重、颜色、描边、行距和相对位置；可以替换底图与本期文案，但不能把黑底带去掉或换成另一套标题样式。

智码航当前 B站 4:3 统一基准为视频 6、7：1440×1080，左侧近黑标题区、右侧人物区并柔和过渡；金色圆角标签，第一行金色、第二行白色、深色描边；标题左对齐并按像素自动缩小，人物与文字不重叠。不得退回竖图居中加两侧模糊柱，或人物居中叠全幅大字的旧布局。

视频 1–4 的 B站 4:3 封面已按视频 6、7 的统一模板重制，本地替换文件不能自动证明平台公开页已经更新。处理这类已发布旧视频时，保留原封面与发布状态的历史记录，把新文件标为“待用户上传/待替换”；只有从公开页核验新封面后才能记为“已更新”。

YouTube 不生成、归档或上传专用缩略图，包括 16:9 横图和 Shorts 9:16 图。此处只验收视频号/抖音共用的 3:4 封面和 B站 4:3 封面。

封面检查：

- 缩略图尺寸下仍能读；
- 最多两三行核心文字，避免整段文案；
- 人脸不被文字盖住；
- 3:4、4:3 两个规格都保住完整钩子；B站 4:3 版还要核对左文右像结构、黑底和缩略可读性；
- 封面事实口径与定稿一致，但不要求逐字复制口播。

## 7. 成片与包验收

先运行本 Skill 的源文件保护型校验脚本：

```bash
python3 scripts/verify_package.py \
  --video <终版.mp4> \
  --cover-vertical <封面.png> \
  --cover-bilibili <封面-横4x3.png> \
  --max-duration <目标上限秒数> \
  --target-lufs -14 --lufs-tolerance 2 \
  --frames-dir <临时抽帧目录>
```

用户选择预览覆盖时，只验证视频，不传两版平台封面参数：

```bash
python3 scripts/verify_package.py \
  --video <预览终版.mp4> \
  --max-duration <目标上限秒数> \
  --target-lufs -14 --lufs-tolerance 2
```

脚本不修改源视频或封面，但 `--frames-dir` 会创建/覆盖抽帧，`--json-out` 会写报告；严格只读审计时省略这两个参数。默认的 1080×1920、H.264/AAC 与两版平台封面尺寸是智码航当前交付规格；项目规格不同时显式传参或只做对应检查。脚本不能识别字幕语义、角标文字、版权或口型。

人工必须完成：

1. 播放首句、末句和每个剪点；
2. 每个分镜至少看一帧，检查字幕、角标、遮挡和画面顺序；重点检查 0 秒和第一个字幕切点，确认第一句实际口播从开头即有对应字幕；
3. 对照锁定稿逐字核对全部字幕、首尾与关键数字，并确认没有混入未口播的封面标题、文档标题、栏目名或标签；
4. 检查嘴型与音轨，无明显漂移；
5. 检查 BGM 稳定、可闻、不压人声；
6. 默认直接上架分支把本期 3:4、4:3 分别与用户指定或当前已验收的同规格基准并排查看；原尺寸和缩略图都要核对标题区黑底/遮罩、字体、字重、颜色、描边、行距、对齐和相对位置；B站 4:3 版额外确认左文右像、标题不越过人物分区且不存在竖向模糊柱；预览分支跳过；
7. 运行一次完整解码，确认没有损坏帧。

任何一项失败，状态仍是 `SOURCE_READY` 或“后期处理中”，不能写 `FINAL_QA_PASS`。
