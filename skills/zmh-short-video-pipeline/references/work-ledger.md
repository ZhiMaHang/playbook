# Work-ledger 归档、台账与 Git

仅在智码航 `work-ledger` 或结构相同的运营仓库中读取本文件。目录、分支和归因规则可能随期次变化，先读当前仓库与上一期文件，再套用本约定。

## 1. 找到本期唯一事实源

先定位仓库根、当前周目录、视频编号和上一期发布物料：

```bash
git -C <候选目录> rev-parse --show-toplevel
rg --files <仓库根> | rg '成片存档/README\.md|w[0-9]+/视频[0-9]+-发布物料\.md|发布记录|geo成长台账'
git -C <仓库根> status --short --branch
```

当前系列通常使用：

- `18.运营获客计划/wN/prod/…`：TTS、源片、字幕、工作流、剪辑参数等过程件；
- `18.运营获客计划/成片存档/视频N/`：终版 MP4、三版平台封面、数字人底图；
- `18.运营获客计划/wN/视频N-发布物料.md`：文案、平台物料、归因、发布 URL 和评论状态的唯一事实源；
- `18.运营获客计划/成片存档/README.md`：成片目录体例与齐备度索引。

沿用实际存在的路径和命名；不要仅凭本文件创建错误的周目录。

`geo成长台账.md` 的视频区用于播放/互动数据，不是存四平台发布 URL 的主位置。文章发布记录也不承载视频 URL。除非当前仓库已经改变体例，发布 URL 只回填本期 `视频N-发布物料.md`。

## 2. 归档边界

成片存档默认只放：

```text
视频N/
  <正式标题>-终版.mp4
  封面.png
  封面-横4x3.png
  封面-youtube-shorts.png
  数字人底图.png/.jpg       # 有则保存
```

不要把分段 MP4、临时字幕图、TTS 试音、工作流缓存和抽帧网格放进归档；它们留在当期 `prod/`。归档说明里对旧“系列共用配乐”的描述只作历史索引，不是新期可复用许可；新期默认无 BGM，禁用清单内的曲目及同源副本不得使用（见 [production.md](production.md#bgm-与响度)）。

归档后同步更新 README 的内容表和齐备度；若某项缺失，写清缺什么，不要提前打全绿。

## 3. 本期发布物料结构

如果本期文件不存在，参考上一期创建；至少包含：

1. 发布成片绝对或仓内相对路径、实测时长/画幅/编码；
2. 发布前事实口径与来源边界；
3. 锁定口播；
4. 三版平台封面与平台用途；
5. 四平台实际标题、正文/简介、标签、AI 声明、分区/可见性和内部归因记录；视频号物料供用户手工发布，抖音/B站/YouTube供第三步发布，抖音另记同步分发；
6. 四平台默认无公司/产品营销的执行记录；若用户明确要求本期加入，记录实际采用的营销文本、事实核验来源和链接位置；
7. 用户已明确要求第四步或提前准备评论时，记录对应平台评论草稿；否则省略；
8. 发布清单；
9. 发布记录与待补项。

智码航当前 YouTube 物料默认使用纯中文标题、简介、标签和评论，不再附整段英文译文；本期内容确需出现的产品名、人物名、技术缩写、命令和外部事实来源 URL 可以保留，自有官网/产品 URL 仍受无营销规则约束。YouTube Shorts 在第二步固定制作、归档 1080×1920 的 `封面-youtube-shorts.png`，第三步发布 YouTube 时上传；普通 YouTube 16:9 专用图不制作。已公开视频改写文案或替换封面时，保留原发布内容、原封面与评论状态作为历史证据，把新稿或新封面记为“待用户替换/待上传”；只有公开页核验后才能写“已更新”。视频 1–4 的 B站 4:3 封面按视频 6、7 模板重制时也遵守该边界。

本期文件必须明确记录四平台简介默认不含公司或产品营销：不自动添加智码航、引见 YinJen、偕行 Stride、产品能力、价格、试用、官网/产品链接或主页引导。只有用户明确要求提前准备评论或启动评论步骤时，才记录评论草稿；草稿只写内容增量和事实边界，且只有用户明确授权评论时才发送。用户明确要求本期加入营销信息时，才记录实际文本、官方事实核验和链接位置；若营销内容进入口播，锁定口播和 TTS 必须已经按第一步重新确认。

发布记录使用清晰字段：

```markdown
| 平台 | 发布状态 | URL | 发布时间 | AI 声明 | 评论 / 置顶 |
|---|---|---|---|---|---|
| 视频号 | 待用户发布 | 不适用（通常无公开链接）；关联抖音作品 ID：待第三步回填（本期不发抖音或抖音未公开时记视频编号＋报告时刻） | 待用户报告（记报告时刻，不是平台发布时间） | 第二步清单已列，用户发布时按清单勾选；未回传不列待办 | 评论未请求 |
| 抖音 | 待第三步 |  |  | 待核验 | 评论未请求 |
| B站 | 待第三步 |  |  | 待核验 | 评论未请求 |
| YouTube | 待第三步 |  |  | 待核验 | 评论未请求 |
```

平台 URL、时间和状态必须来自实际结果。标题不要写“长标题版”；评论不要只写“已处理”。抖音默认开启“同步发布到今日头条”，并在发布物料或发布记录中写明实际开关状态；评论已发但网页版不能置顶时，明确写“评论已发，待手机 App 置顶”。

建议同时记录本期状态。第二步正式发布包完成后记录：

```markdown
> 流程状态：PACKAGE_READY
```

`PACKAGE_READY` 是第二步的正常终点：视频号行记为“待用户发布”，抖音/B站/YouTube行记为“待第三步”，这三个平台的 URL 与发布时间保持空白；视频号的 URL、发布时间两栏按模板写占位说明。用户明确启动第三步后，只按抖音、B站、YouTube实际结果改为 `PUBLISHED_PARTIAL` 或 `PUBLISHED_COMPLETE`；第三步的 `PUBLISHED_COMPLETE` 只表示这三个目标平台都已公开核验。第三步结束时评论栏默认记为“评论未请求”，不自动进入评论步骤；发布证据全部收口且没有请求评论时，可从 `PUBLISHED_COMPLETE` 直接进入 `LEDGER_CLOSED`，评论栏仍保持“评论未请求”。用户明确启动评论步骤后才记 `COMMENTS_PENDING`，再按实际结果改为 `COMMENTS_PARTIAL` 或 `COMMENTS_COMPLETE`；用户明确说本期不需要评论时记为 `COMMENTS_WAIVED`，不再追问或补做。`COMMENTS_COMPLETE` 或 `COMMENTS_WAIVED` 均可进入 `LEDGER_CLOSED`。视频号发布状态按用户回传与关联的抖音同源作品 ID（本期不发抖音或抖音未公开时为视频编号＋报告时刻，抖音之后公开的再补填作品 ID）单独回填；用户主动给了链接就原样括注在台账视频号行的 URL 栏里，标“用户提供、未经公开页核验”，未提供时不列为待补项；AI 声明只记用户回传，不要求前台核验。本期有权利依据“待确认”的素材时，视频号行记“暂缓：权利待确认”，不记“待用户发布”。状态改变以证据为准，不因文件名叫“终版”就自动写 `FINAL_QA_PASS`。

用户说当前视频不行、要重做或要求等待时，状态记为 `SOURCE_REDO_PENDING`，并在文件开头明确写“旧成片、旧封面和旧发布包不得继续发布或评论”（实拍素材＋图卡路线不等新源片：用户给出具体修改意见时重新核验素材、记 `SOURCE_READY` 后按意见重剪，见 [storyboard-motion.md 7.7](storyboard-motion.md#77-参数记录与状态)）。新源片重新走完第二步前，不得沿用旧 `PACKAGE_READY`、旧 URL 或旧第三步授权。

用户明确要求“只做预览”时，状态记为 `PREVIEW_READY`。预览文件留在本期过程目录，不提前写四平台发布记录、不更新正式成片归档与齐备度；需要正式发布包时，再回到第二步制作平台资产并完成归档。第二步完成终版、三版平台封面、四平台物料与正式归档后固定停在 `PACKAGE_READY`，不得填写不存在的 URL 或发布时间。

## 4. 归因

先读取上一期和账号级约定，再决定本期参数。归因默认只作内部记录，不自动写进公开简介或评论：

- 分条平台常用“平台缩写 + 期号”；
- 有的平台可能沿用账号简介的账号级参数；
- 平台不允许或不适合外链时，不强塞 URL；
- 实际发布页没填成功时写待核验，不用计划值代替。
- 发布表单中的标题、简介、封面、AI 声明和可见性必须在提交前完成实际读回；只看到文件名、上传完成或计划文案，不得记为“已填写”。

不要静默把账号级归因规范化成本期参数，也不要在没有落地页约定时自行编造链接。

## 5. 素材权利记录

用户指定外部 BGM、肖像或其他需要授权的素材，以及实拍素材＋图卡路线下载或本技能截取的第三方画面（含用作封面底图的帧）时，至少在本期过程记录或发布物料中写：

```markdown
- 素材：<文件名>
- 来源：<用户提供 / 自制 / 官方渠道下载（发布方、频道、URL） / 本技能截取的第三方页面 / 已购授权 / 平台曲库等>
- 使用范围：<视频号 / 抖音 / B站 / YouTube；商业或非商业>
- 权利依据：<用户确认有权使用 / 授权文件路径；不记录账号秘密>
- 确认日期：<YYYY-MM-DD>
```

没有权利依据时写待确认并暂停公开发布，不自行推断“能下载就能商用”。

## 6. 敏感信息

台账只记业务结果，不写：

- API Key、Token、Cookie、验证码；
- 登录邮箱、手机号、实名信息；
- 私信内容、远程控制凭据或代理订阅；
- 本机配置文件中的秘密值。

可以记录“用户完成频道验证”“浏览器安全策略阻断”“配置存在但未读取秘密值”等非敏感状态。

## 7. Git 提交与推送

本流程每个已获用户授权的步骤完成后，默认自动执行该步骤本期文件的 `git add`、commit 和 push，用户无需再分别说“提交”“push”。按当前步骤限定范围：

| 已授权步骤 | 本期 Git 归档范围 |
|---|---|
| 第一步：音频 | 锁定稿、MP3/WAV、必要的制作与核验记录 |
| 第二步：成片与发布包 | 终版、三版封面、锁定平台物料、必要的脚本/参数/QA，以及归档 README 中本期修改；预览分支仅含过程目录中的预览与 QA |
| 第三步：发布 | 各平台实际发布状态、可靠公开 URL、核验证据与本期台账修改 |
| 第四步：评论，仅在用户明确授权后 | 各平台实际评论/置顶结果、必要证据与本期台账修改 |

第一步达到 `AUDIO_AUTO_QA_PASS` 即执行 Git，实际试听待完成时仍如实保留该状态。第三步或第四步只有部分平台完成、审核中或受阻时，也提交并推送已有的真实结果，不等待全部成功、不把部分完成改写为完成。每个平台仍须即时保存台账，Git 可在本轮已授权范围收口时统一完成。

用户本轮明确要求“只生成本地”“只保留本地”或“不提交”时，保留本地结果且不自动 commit / push；明确“不要 push”时可本地 commit，但不得推送。限制优先于默认，不再重复询问。自动 Git 不授权平台发布、评论或进入下一步骤，也不自动包含技能维护。

每次先做：

```bash
git -C <仓库根> status --short --branch
git -C <仓库根> remote -v
git -C <仓库根> diff -- <本期相关文件>
git -C <仓库根> diff --cached --stat
```

原则：

1. 保护用户原有修改，不重置、不覆盖、不顺手格式化无关文件；
2. 只暂存本期 manifest/清单列出的文件；共享台账或 README 仅包含本期相关修改，不夹带同文件中的无关工作；
3. 大媒体提交前确认仓库允许、文件非临时产物；实拍素材＋图卡路线里含第三方画面的文件按 [storyboard-motion.md 7.3](storyboard-motion.md#73-素材来源下载同意与权利记录) 的仓库可见性规则，可见性未确认时不入库，并在报告里写明；
4. commit 前再次看 staged diff；存在无关已暂存文件时，按本期明确路径隔离提交，保留原暂存区，不清空或混入他人修改；
5. 用户说“全部提交”时，先列出整个工作树并逐项辨别，不把“上次只提两个音频”误报为全量完成；
6. push 前获取已配置上游的最新状态并核对待推送提交范围；没有可确认的上游、会夹带未授权提交、出现冲突或推送被拒绝时保留本期文件、真实结果与已有提交，报告实际阻断，不擅自强推、改 remote 或重写无关历史；
7. push 后从实际远端读回目标分支提交，核对：

```bash
git -C <仓库根> rev-parse HEAD
git -C <仓库根> ls-remote --exit-code <已确认远端> refs/heads/<上游分支>
```

只有远端读回的 SHA 与本次推送提交一致且推送命令成功，才报告已推送；远端随后又有新提交时，可 fetch 后验证本次提交已被远端分支包含。

推送时的几种实测情况：

- 带视频文件的大提交可能推不上去，报 `the remote end hung up unexpectedly`、HTTP 408 或连接中断。HTTPS 远端上，对单条命令临时加大缓冲重试曾经有效（`git -c http.postBuffer=524288000 push …`），不改仓库配置；它对 SSH 远端不起作用，也不是通用解法。网络不稳时按间隔重试有限次数；仍失败就保留本地提交，如实报告。报单个文件超过托管平台上限（例如 GitHub 单文件 100 MB 的 GH001）时重试无效，不再重试，保留本地提交并报告，由用户决定改用 LFS 还是不入库。
- 推送报错之后又显示 `Everything up-to-date`，不能当成功。以远端读回的 SHA（`ls-remote` 或托管平台 API）为准。
- 多人或多个自动化会话共用一个检出时，自己的提交之上可能已叠了别人尚未推送的提交。这时只推到自己那个提交：先用 `git log --oneline <已确认远端>/<上游分支>..<本期提交SHA>` 确认列出的只有本期提交（祖先里有别人未推送的提交时，按上方第 6 条报告阻断），再执行 `git push <已确认远端> <本期提交SHA>:refs/heads/<上游分支>`。核验时拿 `<本期提交SHA>` 与远端读回结果比对，不用 `HEAD`。

每个已授权步骤均须落实自动 Git，不能在第二步交付、第三步发布或第四步评论结束后再次等待提交/push口令。没有本期新改动时不创建空提交，核对现有本期提交是否已推送；有未推送提交时仍先检查其授权范围。保存、commit、push 分别说明；不要把推送成功当作实际试听、平台公开发布或评论成功。

## 8. 交付清单

以下清单按三步主流程和可选评论规则收口。用户明确只做预览时，只交付过程目录中的预览终版和视频专项 QA 结果，状态记为 `PREVIEW_READY`；不要求三版平台封面、平台 URL、正式归档或 README 更新。

每个已授权步骤最终回复均需列出本期自动提交 SHA、目标仓库/分支和远端核验结果；失败或用户明确限制时说明 Git 实际状态。步骤完成后不再单独询问是否提交或推送。

第二步最终回复至少列出：

- 终版视频、三版平台封面、发布物料的绝对路径；
- 视频号手工发布所需的成片、3:4 封面、短标题字符数、简介和 AI 声明清单；
- 本期有权利依据“待确认”的素材时，列出这些素材，并提示视频号也应等权利依据补齐后再发，由用户决定；
- 抖音、B站、YouTube物料已准备但尚未上传，所有公开 URL 保持空白；
- 四平台正文/简介已按默认规则去除公司与产品营销；若用户明确要求本期加入，已记录实际文本与事实核验；
- 评论不是第二步默认交付；若用户已明确要求提前准备，则报告无营销评论草稿已锁定但尚未发送；
- 状态为 `PACKAGE_READY`，以及视频号待用户发布（有“待确认”素材时为“暂缓：权利待确认”）；
- 成片 README 是否已更新；
- Git 是否未提交、已 commit 或已 push，以及对应 SHA。

第三步最终回复至少列出：

- 抖音、B站、YouTube各自的准确公开 URL、实际标题、AI 声明和公开/审核状态；
- 抖音是否实际开启“同步发布到今日头条”；
- 视频号由用户发布：记录用户报告时刻及关联的抖音同源作品 ID（第三步抖音公开后回填；本期不发抖音或抖音未公开时，以视频编号＋报告时刻登记）；视频号分享链接一般只能在微信内打开、无法从公开网页核验，不把 URL 列为用户待办；用户主动给了链接就原样括注在台账视频号行的 URL 栏里，标“用户提供、未经公开页核验”；
